# AutoKolab efficiency audit

Audit date: 15 October 2026. Scope: the code on this branch, after AK-146 and AK-147's read reductions. This report distinguishes observations from calculations and estimates; it does not treat the earlier 18.86 GB Supabase egress figure as today's baseline.

## Evidence and limits

The code paths and timer intervals below are measured from the repository. The ticket reports 18.86 GB of Supabase egress against a 5.5 GB allowance, roughly $0.61 per review, and eight agent turns in two loops. Those figures are reported observations, not independently verified samples. A member-authenticated live query was attempted with `autokolab whoami`, but sign-in failed with `fetch failed` in this sandbox. Live `run_usage`, table sizes, and runner logs were therefore unavailable. Every daily byte, token, and dollar figure below is explicitly an estimate until those three sources can be read.

The 18.86 GB figure has no time window in the ticket and predates the two quick fixes. It cannot be divided into a valid daily rate or attributed to a particular query. `run_usage` contains engine reported tokens and cost, but no prompt bytes or database bytes; Codex can report a null cost. The runner's ten minute download log counts `JSON.stringify` bytes for selected `ProjectView` reads only, so it is neither complete network egress nor a replacement for Supabase's metric. [Runner counter](../../packages/autokolab/src/runner/runner.ts), [run record schema](../../packages/autokolab/sql/020_run_usage.sql).

The MCP tools themselves are **on demand**, not a polling loop. `whoami`/`agents` read identity and project names; `room_read`/`room_wait`/`room_thread` read cursor-bounded messages (wait also holds a scoped Realtime subscription); `work_log` reads recent task runs and their messages; `board_list` reads up to 200 bulletin rows; `project_brief` constructs the full guide/board text; `tickets` reads ticket lists; `ticket_get` calls `ticketText()` with full ticket, steps, comments, all tickets, links and decisions; `decision_get` reads decisions. Write tools (`room_post`, question close, board upsert, ticket create/update/comment/steps, guide update, decision add, model change, approval) make their corresponding RPCs or writes and may read the result or full ticket first. The per-tool presence wrapper can itself read `agents.select(*)`, resolve a project and write status for standalone MCP use. None of these should be counted as idle recurring calls, but repetitive model tool use can dominate a busy run. [MCP registrations](../../packages/autokolab/src/mcp/server.ts).

Realtime subscriptions per runner are `messages` INSERT team wide and `members` UPDATE team wide; each project adds `tickets` all changes filtered by project, `ticket_comments` INSERT **unfiltered**, and `ticket_links` all changes **unfiltered**. A callback invalidates every project's light cache, so an unrelated comment or link can make every runner reload a project board. [Subscription definitions](../../packages/autokolab/src/core/client.ts), [project subscriptions](../../packages/autokolab/src/core/projects.ts). Realtime payloads can add egress even when no REST reread follows. The client cannot infer server fanout cost from this code.

## Daily cost model

These are **scenario estimates**, with arithmetic shown so they can be replaced by actual counts. One project has 170 tickets, four online runners and one browser tab left visible on Overview for 24 hours. A light ticket row is assumed to be 0.45 KB, a site ticket row 0.35 KB, a full ticket row 2 KB, and the site workspace refresh including steps/guide/people 100 KB. These values are assumptions, not samples from Supabase. They describe **response payload**, not total billed egress; TLS, JSON wrappers, Realtime fanout and other consumers could make actual egress higher. The idle scenario has no ticket/message changes. The busy scenario adds 100 ticket/step/comment changes, 200 room messages, and 20 model runs (8 builds, 4 reviews, 6 replies, 2 triages). Some changes may coalesce in the 150 ms site debounce, so the busy estimate assumes they are separated.

| Source | Idle estimate/day | Busy extra/day | Calculation and uncertainty |
|---|---:|---:|---|
| Four runner light board snapshots | 86 MiB | up to 30 MiB | 170 × 0.45 KB × 288 five-minute refreshes × 4; extra 100 invalidations × same × 4. The 120 s poll usually hits cache. This is the largest estimated **idle REST** source. |
| Runner heartbeats/status/usage and five-minute project reload | 12–30 MiB | under 5 MiB | Four × 2,880 cycles × an assumed 1–2 KB combined response, plus project/member reloads. Writes may also drive Realtime egress. |
| One visible workspace and Captain room safety reads | 28–36 MiB | up to 10 MiB | 100 KB × 288 refreshes = 28 MiB; extra 100 separated changes × 100 KB. Empty room cursor reads have small responses; initial 300 messages is extra and depends on length. |

## Leaner operating design

**Change detection.** Treat Realtime as a low-latency hint, not the only source of truth. Each runner owns a durable per-project cursor. A changed-ticket event wakes a narrow `tickets` query for IDs changed since that cursor; comments use their existing numeric ID cursor; message reads already use `id > lastSeenId`. Group hints for 250–500 ms and make one read per affected project. Advance a cursor only after applying rows. Handle deletion with tombstones or the existing event log where it proves complete; if not, add a tiny project change journal in a separately approved migration. Reconcile a full light board on startup, reconnect and every 12–24 hours, with jitter, so missed Realtime events cannot strand work. Older helpers can keep the five-minute full-light scan until both sides support cursors. A paused runner should still see owner pause changes promptly, but should avoid full board scans. Keep one owner for each delivery action: ticket state starts build/review/merge, a room message asks or answers, and a status notice never starts work.

**Prompt assembly.** Give each run a purpose-specific packet. Build: the current full ticket, exact new comments, machine safety rules, project identity, and only decisions cited by the ticket or files it touches; let the agent request other guide sections when needed. Reply: only new messages, a short thread summary and the specific ticket fields needed to answer, with no full-board read. Triage: the question, ticket and cited decisions. Review: changed files, checks, bounded diff, exact SHA, done means and relevant decisions; retain local checkout access for context. Cache guide/decision versions on the helper and make MCP reads cursor-aware; never silently truncate an instruction or evidence. If a ticket itself exceeds the prompt budget, send a short index and require an explicit full `ticket_get` before work. On resume, send the delta; start a fresh session with a bounded summary when retained context is no longer useful or its token cost exceeds a fresh run.

**Wake policy.** A person's direct instruction starts the owning run immediately. A teammate's question starts one batched, read-only reply only if an answer is needed. A teammate's task/review about an owned ticket becomes a note for its build/review run; it does not earn a separate acknowledgement run. Correlate replies to the specific request ID and let only a new question wake another model. A status, approval, review result, automated notice, and an agent's acknowledgement are recorded but do not wake a model. Keep AK-149's hard cap as the final guard; a repeated ask after a complete answer needs a new human or ticket change, not another agent turn. Captain should answer a worker's `needs_human` once per distinct question text, then wait for a changed ticket or a person; its own answer must not create a new triage question.

**Enforceable budgets, proposed defaults.** These are engineering targets for a future ticket, not measured present behavior. Count actual bytes/tokens before enforcing and keep project owners able to set tighter local limits.

| Budget | Proposed default and enforcement |
|---|---|
| Idle database download | **≤2 KB/min per runner**, averaged over one hour, excluding one startup reconciliation; **≤5 KB/min per visible tab** excluding its first load. Record HTTP response and Realtime payload bytes separately. Alert at 2× for one hour; do not stop essential pause/message checks. Today the example runner light board alone is roughly 15 KB/min. |
| Briefing | **≤24 KB initial injected text**, with at most **8 KB unrelated project context**; **≤8 KB reply**; review diff **≤60 KB** as today but report when it is cut. Overlong tickets remain accessible in full through `ticket_get`, and the run must read them before editing. Log bytes and estimated tokens by section; alert, then enforce only after observing real distributions. |
| Agent conversation | **One request → one answer**, with at most one new clarifying question and one answer before stopping. The hard cap should count both room and ticket-comment turns across restarts. AK-149 owns implementation of the cap; do not create a competing one here. |
| Model work | Keep the existing owner task-minute and daily time limits and OpenCode `daily_usd` stop. Add per-kind soft targets from measured p90 tokens/turns and warn Captain at 75% of an owner's existing spend cap. Stream usage to stop near the cap when supported; never record null cost as zero or imply a hard cap can work without reported cost. |
| Retries | Automatic retries for transient network/provider failures with bounded backoff (1, 5, 30 min); one active run per event ID/SHA and at most three failed starts per ticket per day. Escalate the concrete cause after that, not on the first transient failure. |

**Measurement and alerting.** Add a small numeric usage event per run and per client hour: REST bytes by route/table, Realtime bytes and reconnects, number of safety scans, prompt bytes by section, input/cache/output tokens, cost if reported, wake reason, run outcome and failure class. No prompts, source code, room bodies, secrets or raw transcripts go to Supabase. Keep local detailed logs for diagnosis; store only aggregates on the server. Results can show one plain line, for example: “Today: 20 runs; 491k reported tokens; $7.20 reported cost; 180 MiB downloaded (estimate until instrumented).” A click gives per-kind and per-source rows, missing-data counts, and a comparison with the previous seven local days. Alert Captain on persistent idle egress above budget, a rise in failed runs, or repeated agent turns; notify a person only when a decision or actual intervention is needed.

## Decision points and verification

The next implementation should begin with real samples for one quiet day and one busy day. The important outputs are (a) actual Supabase egress/day, (b) request and Realtime bytes by source, (c) `run_usage` p50/p90 by kind and model with null coverage, and (d) the fraction of messages that woke, merged or were ignored. Compare the same number of runners and visible tabs before and after each change. A claimed saving fails verification if total billed egress does not fall or if missed changes, delayed pause, incorrect review, or a higher retry rate offsets it.

No product choice is needed for this research report. A later project-change journal would be a database change and needs Captain's normal big-work approval before its ticket starts. The user-facing design should stay a simple Results line with inspectable evidence, in keeping with the project's one-fact-per-place rule.
