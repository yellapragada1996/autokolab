These are the proposed common names: nine agent statuses and seven ticket statuses. AK-182 applies them only to Overview. Backlog and Ready remain distinct scheduling values in the database; **To go** is their truthful glance-level grouping. Review belongs to a ticket; Reviewing belongs to a live agent. Color identifies a status family, and the word identifies the exact state.

A blocked ticket uses one of these specific problem labels, rather than the umbrella word when the cause is known:

| Problem word | Proof | Who acts / when it clears |
| --- | --- | --- |
| Run failed | `tickets.needs_human` begins `I stopped: `; the runner writes this only after an error or a run timeout. | Agent's owner checks the reason and retries; clears when the report is removed. A timeout is an unsuccessful run, not proof of a daily allowance or automatic resume. |
| Checks failed | `(tickets.checks ?? tickets.pr_facts.checks).state=failure`. | Builder fixes the check; clears when the recorded check result changes. A GitHub check is not necessarily a test case, and this never marks its agent Failed. |
| Limit reached | The selected builder's supported limit state, on that same in-progress ticket. | Normally nobody; the timestamp is an expectation, not a promise. |
| Blocked | Other `RUNNER_PROBLEM` reports or the selected builder's generic blocked state. | Owner follows the recorded reason; no failure, pause or resume time is invented. |

The red labels all use the same solid bar and ring. Their visible words are the second cue: no dash, mask, gap, pattern or cut inside the red segment. Segment spacing between separate tickets is retained. On a ticket with several problems, checks take precedence over a failed run, then a usage limit, then a general block; the runner's reason remains in the accessible description. An explicit question takes priority for the ticket's main status, with any check failure retained in its description; the request remains actionable in Captain. Closed tickets do not acquire a current problem status.

Agent precedence is Paused → Offline → Limit reached → live Reviewing/Working → Waiting on you → Failed → Blocked → Idle. Problem reports on a ticket remain visible even while its builder is running again. An agent's live failure cannot be inferred from assignment, a failed check, a paused thread, or a missing heartbeat. One agent's selected ticket cannot turn its other assignments red. Foreign-project work may say Working in another project but never reveal its ticket or note or count as this project's live work.

**Timing and limits of the current data.** The runner checks in every 30 seconds (`runner.ts`, `HEARTBEAT_MS`). Overview evaluates age/expiry when it receives a changed workspace or Captain snapshot. Project subscriptions have a five-minute visible-tab safety poll (`lib/poll.ts`), but identical snapshots are preserved: this is not a wall-clock guarantee that the label changes at exactly five minutes. It keeps the last complete view on a failed refresh and labels that view stale. No timer or new fetching is added here. Precise expiry on an otherwise unchanged screen needs a scoped follow-up.

`waiting_until` does not distinguish daily time, provider usage or rate limits. Do not say “daily” without specific evidence. Old notes without a timestamp remain reports until replaced; do not invent a reset. `run_usage` reports cost and work but has no success/failure outcome; Overview does not load room run history. General chat/review failure status, a structured latest-run outcome/cause, limit kind and spend reset timestamp need runner/database reporting before they can be shown. Project-wide Paused also needs a real switch. None is built in this ticket.
